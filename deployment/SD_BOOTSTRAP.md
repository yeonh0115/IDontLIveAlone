# Existing Pi A SD installation

Do not format or run Raspberry Pi Imager against this card. The inspected bootfs identifies a 2025-12-04 Raspberry Pi OS image and contains `user-data`, `meta-data`, and `network-config`. Raspberry Pi introduced cloud-init in its 2025-11-24 image; previous systemd first-run customization is a separate format. Do not change the existing cloud-init instance ID, account definitions or network settings to rerun initialization. [Official Raspberry Pi announcement](https://www.raspberrypi.com/news/cloud-init-on-raspberry-pi-os/) · [Imager customization formats](https://github.com/raspberrypi/rpi-imager/blob/main/doc/os_customisation_formats.md)

Before choosing a bootstrap route, inspect the ext4 root read-only: `/etc/passwd`, `/etc/fstab`, `/usr/lib/systemd/system-generators/systemd-run-generator`, existing camera/face units and autostart entries, the original project directory, `ai_env/bin/python`, `trainer/trainer.yml`, `trainer/user_map.txt` and `facedata`. A model found only as root-level `trainer.yml` needs an explicit map/path decision; the installer stops instead of silently starting from an empty model.

The preferred installation is an ordinary root invocation of `install_camera.py` from an already available Linux shell or a mounted Linux root with a reviewed first-boot service. Its default mode validates and prints a plan. `--apply` copies only Pi A source files and the common helper, makes a private `/var/backups/idontlivealone/<timestamp>` backup of original code/config/services/model/data, keeps the existing virtual environment, and enables `idla-camera.service` / `idla-face.service` for the next normal boot. It performs dependency imports but does not drive GPIO, start the camera, contact the network, install packages or alter the operating system. Old services are disabled only by exact `--disable-service` arguments established during inspection. Existing desktop/crontab/manual launchers must also be reviewed to avoid two processes competing for the camera or GPIO.

If only the FAT boot partition can be written, a dedicated one-shot boot command is a candidate after rootfs verification. Systemd's documented `systemd.run` generator can run a command as a regular one-shot service; separate success/failure actions control what happens afterward. Raspberry Pi Imager's older implementation used that feature. This can install files without rerunning cloud-init, but this repository deliberately does not arm or rewrite `cmdline.txt` automatically. The actual card's boot mount and generator must be verified first. The original single-line command line must be privately backed up and restored by a reviewed wrapper on both success and failure, without deleting unrelated kernel options. [Systemd primary documentation](https://github.com/systemd/systemd/blob/main/man/systemd-run-generator.xml) · [Raspberry Pi Imager source](https://github.com/raspberrypi/rpi-imager/blob/v1.8.5/src/OptionsPopup.qml)

For a headless connection code, run the shared enrollment CLI on the PC immediately before installing the prepared identity. Keep its state outside Git and copy only `credentials.json` into the card's private provisioning payload. The same token resumes registration after a lost response. Only the eight-digit code is shown; enter it in the Android app while valid. Pair the prepared identity before first Pi boot if convenient. The Pi does not need its IP address or account number: it fetches its account through authenticated status polling. Never provision CAMERA and SENSOR with the same credentials.

FAT has no Linux permission enforcement. The temporary credential on bootfs is confidential despite a `.json` extension. Transfer it to the existing user's Linux `device_state/credentials.json` with mode `0600`, then remove the staged credential and any credential-bearing archive after successful verified installation. Keep the PC backup private. Do not place tokens in `cmdline.txt`, service arguments, README, screenshots or Git. The installer does not delete the source credential itself because the coordinator must first verify the copy and recovery plan.

Example plan on the Pi, with all paths replaced by verified values:

```sh
sudo /usr/bin/python3 /boot/firmware/door-payload/deployment/install_camera.py \

```

Append `--apply` only after reviewing that plan. No SD-card write or hardware validation is implied by the included mock tests.

The user requested no event-photo storage. This installation writes `EVENT_PHOTOS_ENABLED=false`; the manifest must use `eventPhotosEnabled:false`. Do not pass `--event-photos-enabled`. Sensor logs, generated reports, live video and the existing face model remain available. The server also uses the same disabled photo policy.

The inspected card now confirms Debian 13 Trixie, the systemd generator, the `/boot/firmware` mount, the existing `yeonh0115` account and `/home/yeonh0115/cctvStreaming/ai_env/bin/python` environment. Its model/map live under `trainer/`. Its actual face parameters differ from the old PC backup: **SOLENOID_PIN=24, FACE_THRESHOLD=80, FACE_REQUIRED_SUCCESSES=2**. Pass these three explicit installer arguments. The existing `camera_stream.service` launches `video.py`; pass that exact unit name to `--disable-service` after confirming its role. The old CIFS `images/` automount is not used or traversed by the new code or installer. Its credential-bearing fstab entry must not be printed or copied into a public artifact.

`bootstrap_camera.py` and `door-bootstrap.sh` implement the reviewed one-shot wrapper. The coordinator stages the shell wrapper as `/boot/firmware/door-bootstrap.sh`, the source-only payload under `door-payload/`, the exact original command line as `door-original-cmdline.txt`, and a `door-bootstrap.json` manifest. The manifest contains version 1, the original command line SHA-256, `rootPartuuid`, SHA-256 for every path in `PAYLOAD_FILES`, existing user/project/Python paths, the three actual device parameters, reviewed disabled service names and a `preparedCredential` flag. It contains no token. Prepared credentials are a separate `door-credentials.json` file.

The pure `armed_cmdline()` builder returns the original line plus only the four dedicated systemd options. It rejects any existing systemd boot override. The wrapper checks the original checksum/root partition and the exact armed line, then restores the original bytes **before** installation. A changed payload stops installation after restoring normal boot. Unrelated edits to the armed command line are preserved and cause an error. Success reboots; failure powers off to prevent an installation loop. With a restored command line, the next power-on follows normal boot. A token-free `door-install-result.json` records the result. The temporary FAT credential is removed only after verifying that the installed private credential is identical. This wrapper has mock tests for recovery and integrity; actual boot execution remains the coordinator's responsibility.

## Local bundle and final arm sequence

After deploying the enrollment API, run `device_client/device_pairing.py --state-dir PRIVATE_DEVICE_STATE --role CAMERA --name Door-camera` on the PC. It prints only the eight-digit pairing code and expiry. Enter that code in the logged-in Android app; no Pi IP or user number is required. Reusing the same state folder preserves the token and returns the same live code until expiry. Do not create another token just because an HTTPS response was lost.

Run `deployment/prepare_camera_bundle.py --output NEW_PRIVATE_PC_BUNDLE --original-cmdline F:\cmdline.txt --credential PRIVATE_DEVICE_STATE\credentials.json`. The builder reads the card command line but only writes the PC output folder. It checks the reviewed root PARTUUID, validates the prepared CAMERA credential without printing it, copies the exact source payload, generates all checksums and the actual 24/80/2 card settings, and writes `door-armed-cmdline.txt` as a separate staging file. It never writes `cmdline.txt` or edits an SD volume. Use a new private output folder each time; nonempty output is rejected.

The coordinator then rechecks the card identity and original command line checksum, copies `door-payload/`, `door-bootstrap.sh`, `door-bootstrap.json`, `door-original-cmdline.txt`, and confidential `door-credentials.json` to the bootfs root, and verifies the copied bytes and payload hashes. Only after those checks should the coordinator copy the prepared `door-armed-cmdline.txt` bytes over the card's `cmdline.txt` as the final step. Keep the exact original backup and full image backup on the PC. Flush/eject safely before Pi power-on. A source change after bundle generation requires generating a fresh bundle and new hashes.

The installer units depend on `network.target`, not `network-online.target`: local capture and existing-model recognition start without waiting for Wi-Fi or Render. Only cloud threads wait for pairing/status. No installer or bootstrap step starts a camera or GPIO action before the normal reboot. The common helper preserves `paired-owner.json` alongside credentials so an unlink/restart/re-pair to another account cannot silently reuse the previous account's face data or outbox; review an intentional account migration separately.
