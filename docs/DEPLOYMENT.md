# 수정본 적용 안내

이 브랜치는 서버·앱·Pi A를 함께 바꾸는 수정본입니다. GitHub 소스 백업은 DB, Render에 업로드된 사진, Pi의 기존 학습 모델을 백업하지 않습니다. 이번 작업에서는 운영 DB와 장치에 접속하거나 배포하지 않았습니다.

## 변경 사항

- 얼굴 등록 접수와 학습 완료를 구분합니다. 앱은 `SUCCEEDED`를 확인한 뒤 완료를 표시합니다.
- `face_tasks` 테이블에 작업 상태와 임대 정보를 저장합니다. Pi가 중단되면 임대 만료 후 재전달하고, 결과 재전송은 중복 처리하지 않습니다.
- Pi는 같은 기기의 카메라를 기본 `127.0.0.1:5002`에서 읽습니다. 설정으로 다른 주소를 지정할 수 있습니다.
- 카메라 프로세스 종료 시 재기동하고 오래된 영상은 비웁니다. 외부 HTTPS/WSS의 인증서 검증을 사용합니다.
- `/api/upload`는 `userNo`를 요구합니다. 첫 사용자로 대체하지 않으며, 동일 사용자·`log_id` 재전송은 기존 사진을 반환합니다. 자정을 넘긴 재시도도 최초 이벤트 날짜에 연결됩니다. 서로 다른 사건에는 고유한 `log_id`를 사용합니다.
- 기존 일별 리포트의 사진 URL을 덮어쓰지 않고 추가합니다. `photo_url`은 TEXT로 확장됩니다. 사진 하나만으로 고위험 사건 1건을 만들어내지 않습니다.
- 앱은 조회 실패, 기록 없음, 실제 위험 0건을 구분하고 카메라 권한을 요청합니다. 음성 전송은 WSS를 사용합니다.
- 조회 요청으로 모든 리포트를 지우던 `/api/reports/setup-test`를 제거했습니다.
- Docker 빌드에서 서버 테스트를 실행하고, 실행 이미지는 초기 Java 21 EA 버전에서 정식 Java 21 JRE 이미지로 변경했습니다. 사용한 `21-jre-jammy` 태그는 [공식 이미지 목록](https://github.com/docker-library/official-images/blob/master/library/eclipse-temurin)에서 확인했습니다. 이 PC에는 Docker 실행기가 없어 컨테이너 빌드 자체는 검증하지 않았습니다.

## 서버 설정

| 환경변수 | 설정 |
| --- | --- |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | 기존 Aiven 연결값을 Render 환경변수에 유지 |
| `PUBLIC_BASE_URL` | 공개 HTTPS 주소. 기본값 `https://idontlivealone.onrender.com` |
| `STORAGE_DIR` | 실제 영속 디스크의 경로. 예: `/var/data` |
| `FACE_WORKER_DEVICE_ID` | 이 서버의 Pi A 식별자. 기본 `door-camera-a`; Pi `DEVICE_ID`와 동일하게 설정 |

사진은 `STORAGE_DIR/pictures`와 `STORAGE_DIR/uploads`에 저장됩니다. 기본 `./data`는 개발용 경로이며, 운영에서 사진 보존을 보장하지 않습니다. Render의 기본 파일시스템은 재배포·재시작 시 파일이 사라질 수 있고, 실제 영속 디스크의 마운트 경로 아래만 보존됩니다. 현재 서비스의 요금제와 디스크 연결 여부는 확인하지 않았습니다. [Render 공식 문서](https://render.com/docs/disks)

현재 존재하는 `pictures/`·`uploads/` 자료는 새 배포 전에 별도 보관하고 영속 디스크의 대응 하위 폴더에 옮겨야 합니다. 서버는 이전 경로도 읽기 호환용으로 제공하지만 이전 인스턴스의 파일 자체를 복구하지는 못합니다.

기존 JPA `ddl-auto=update` 설정은 새 `face_tasks`, `event_photos` 테이블 및 `daily_reports.photo_url` 확장을 적용합니다. 운영 적용 전 Aiven의 별도 백업과 스키마 변경 권한을 확인해야 합니다. 이 브랜치에서 실제 DB 마이그레이션을 실행한 것은 아닙니다.

## Pi A와 앱 적용

1. Pi의 기존 `trainer/`, `facedata/` 및 설정을 별도 보관합니다. 이전 작업 디렉터리에 모델이 있었다면 새 `PI_DATA_DIR`를 그 위치로 지정합니다.
2. `raspberrypi/`의 실행 파일과 `pi_runtime.py`를 함께 복사하고 README의 환경변수를 설정합니다. `USER_NO`는 이 장치가 속한 앱 계정의 실제 숫자 사용자 번호입니다. 미설정이면 이벤트 업로드가 명확히 실패합니다.
3. 서버와 Pi를 같은 수정본으로 전환하고, `android/`에서 빌드한 앱을 설치합니다. 기존 Pi의 작업 결과 형식과 기존 앱의 즉시 성공 표시는 새 계약에 맞지 않으므로 세 부분을 함께 적용합니다.
4. Pi B의 기존 `/trigger_event` 호출 경로는 유지됩니다. 재시도 시 같은 이벤트를 유지하려면 `log_id`를 전달해야 합니다. Pi B가 서버 `/api/upload`를 직접 호출한다면 `userNo`도 추가해야 합니다. Pi B 코드는 이번에 수정하지 않았습니다.

## 실제 장치에서 확인할 항목

- 처음 설치한 앱에서 카메라 권한 허용·거부가 정상적으로 안내되는지.
- Pi가 꺼져 있을 때 얼굴 등록이 대기 상태로 보이고, 켜진 뒤에만 완료되는지.
- 카메라 프로세스 중단 후 영상이 복구되는지.
- 기존 등록 얼굴이 유지되고 GPIO 23 신호가 실제 FPGA 결선에서 3초간 출력되는지.
- 같은 `log_id`를 두 번 보냈을 때 사진이 한 번만 저장되고, 서로 다른 이벤트는 둘 다 표시되는지.
- 서버 재시작 뒤 대기 작업과 사진을 다시 조회할 수 있는지.

## 범위와 남은 제한

이 변경은 동작 신뢰성 개선입니다. 기존 서버의 사용자 ID/번호 기반 요청 구조에는 세션/JWT 기반의 전체 인증·권한 체계가 없습니다. `DEVICE_ID` 역시 비밀 인증키가 아닙니다. 사용자 인증과 비밀번호 저장 방식의 보안 개선은 별도 작업이 필요합니다.

얼굴 인식 성공을 위험 이벤트로 자동 기록하거나, Pi B의 센서·음성 기능, YOLO, 푸시 알림을 새로 구현하지 않았습니다. 생체 위조 방지와 실제 인식률 검증도 포함하지 않습니다.

문제가 생기면 GitHub의 수정 전 백업 브랜치에서 앱·Pi·서버 소스를 복구할 수 있습니다. DB와 사진·학습 모델은 별도로 보관한 백업을 사용합니다.
